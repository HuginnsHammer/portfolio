CloudSentry

A local scanner that checks Terraform, Dockerfiles, and Docker Compose files for a defined set of risky configuration patterns.

View source on GitHub ↗

What it does

CloudSentry reads configuration files and reports findings with a rule ID, severity, source location, evidence, impact, and a suggested fix. It has a command-line interface, JSON output, a FastAPI endpoint, and a React + TypeScript dashboard. Scanning is static: it does not apply Terraform, build images, start containers, or execute the files it reads.

Implemented scope

  • Terraform: checks for public S3 ACLs, world-open AWS security-group ingress CIDRs, and EBS volumes with encryption explicitly disabled.
  • Dockerfiles: checks for an explicit root user, mutable latest base-image tags, and a missing USER instruction.
  • Docker Compose: checks privileged services, host networking, Docker socket mounts, and wildcard host-port bindings.

That is 10 documented rule IDs across three configuration formats. The repository CI runs Python tests and lint checks on Python 3.12 and 3.13, and builds the frontend.

Example: reviewing a Terraform fixture

The repository includes examples/terraform/storage.vulnerable.tf. It deliberately sets an S3 ACL to public-read and an EBS volume to encrypted = false. Those two literal settings map to the following implemented checks:

CS-TF-001 · Critical

aws_s3_bucket_acl.assets — S3 bucket ACL allows public access.

Evidence: acl = "public-read"

Remediation: Remove public ACL grants and enforce S3 Block Public Access and least-privilege bucket policies.

CS-TF-003 · High

aws_ebs_volume.data — EBS volume encryption explicitly disabled.

Evidence: encrypted = false

Remediation: Enable encryption and define an approved KMS key policy where required.

This is a walkthrough of the committed fixture and matching rule implementation, not a claim that these settings were found in a live cloud account. The sample is intentionally vulnerable test data.

One design choice

CloudSentry runs locally and uses static parsing instead of deploying or executing the configuration. That keeps a scan simple to repeat and avoids needing cloud credentials, but it also means the scanner cannot determine the final effective permissions or network exposure of a real deployment.

Known limitations

  • Terraform checks use literal parsed values; variables, locals, modules, dynamic blocks, provider defaults, and effective policies are not resolved.
  • Dockerfile checks are line-oriented and do not fully model multi-stage inheritance, build arguments, or orchestrator overrides.
  • Compose line mapping is best-effort, and only supported service structures are checked.
  • Rules can miss issues or report patterns that are acceptable in context. A clean scan is not proof that a configuration is secure.

Tests and CI

The test suite includes positive and negative cases—for example, it checks that a public S3 ACL is detected, a private ACL is not, world-open ingress is reported, restricted ingress is not, and world-open egress is not misclassified as ingress exposure. The repository's GitHub Actions workflow has a successful run on the current default branch.
