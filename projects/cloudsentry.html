PROJECT / CLOUD & INFRASTRUCTURE SECURITY

CloudSentry

A work-in-progress security tool exploring how infrastructure-as-code can be reviewed for risky configuration patterns before those patterns become operational problems.

In progress — verify current branch before relying on implementation details

The problem

Infrastructure configuration is executable intent: small choices around access, network exposure, secrets, and execution context can create meaningful risk. A useful reviewer should make suspicious patterns easier to identify and explain, while being clear that static checks are not a complete security assessment.

Project goal

CloudSentry aims to provide a practical workflow for examining infrastructure-as-code and presenting findings in a form a developer can investigate. The intended value is repeatability and explainability, not a claim that automated rules can prove a deployment secure.

What to verify in the repository

This portfolio entry deliberately avoids asserting that a feature is production-ready without a fresh review of the source and CI results. Before describing a capability as complete, verify its implementation and tests on the current default branch.

  • Supported input formats and parser behavior, including malformed or unexpectedly large files.
  • Rule identifiers, rationale, severity, and examples for each implemented check.
  • How the scanner handles paths, symbolic links, and files outside the intended scan scope.
  • CLI and API behavior, including error handling and limits on untrusted input.
  • Frontend build status, API integration, and tests that exercise user-visible behavior.

Security and engineering considerations

A configuration scanner processes files that may be untrusted. Path handling, parser limits, predictable errors, and safe rendering of finding details matter. Findings should include enough context to be actionable without exposing secrets from scanned files.

The tool should also distinguish a detected pattern from a confirmed exploit. Rules can produce false positives and false negatives; deployment context determines whether a finding is actually exploitable.

Evidence and next steps

  1. Run the documented test suite and full CI on the branch intended for release.
  2. Confirm parser and rule coverage with representative positive, negative, and malformed-input fixtures.
  3. Review API path handling and resource limits; ensure UI output safely displays untrusted values.
  4. Record verified screenshots or sample output using sanitized, non-secret fixtures.
  5. Update this page with measured results, known limitations, and a release or demo link only after verification.
